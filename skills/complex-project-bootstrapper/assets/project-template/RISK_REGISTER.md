# Risk Register

| Risk ID | Risk | Likelihood | Impact | Early warning | Mitigation | Owner | Status |
|---|---|---|---|---|---|---|---|
| R-001 | Chat history diverges from repository state | Medium | High | Different models cite different facts | Read state files at startup; update handoff and commit | Project owner | Open |
| R-002 | Sensitive information is committed to Git | Low | Critical | Secrets or unredacted originals appear in working tree | Private repo, `.gitignore`, source index, secret review | Project owner | Open |
| R-003 | An AI performs an unauthorized external write | Low | High | Send/push/delete/permission action without clear approval | Read-only defaults and explicit approval boundary | Project owner | Open |
| R-004 | A writable local approval record is mistaken for human authentication or a security sandbox | Medium | High | Claims that the gate controls hostile code or untrusted actors | Document the workflow-integrity boundary; retain external permission controls; fail closed on missing/runtime-unverifiable state | Project owner | Known limitation |
| R-005 | Distributed skill/template copies omit the current gate | Low | High | Payload drift or generated project missing gate files | Synchronize canonical/native/standalone payloads; CI --check plus real standalone generation tests | Maintainer | Mitigated for Issue #2 |
| R-006 | Packet state, role labels or evidence strings are mistaken for verified external outcomes or execution authority | Medium | High | A recorded VERIFIED/MERGED state is cited as proof without checking real evidence | Explicit metadata-only CLI/docs; preserve revision/role/state checks; future executor enforces bootstrap and actual evidence/review controls | Maintainer | Known boundary; operational controls remain later issues |
| R-007 | Synthetic routing estimates or supplied history are mistaken for measured performance, complete usage or a hard spending limit | Medium | High | Enabling fictional models or treating replay as authentication/billing enforcement | Disable example resources; document per-role caps and estimate provenance; preserve original decision inputs; later executor/telemetry must verify live access, reserve usage and collect accepted-result observations | Maintainer | Known boundary; #4 is offline selection |
| R-008 | A local feedback record is treated as real execution, fresh dependency state or globally complete usage | Medium | High | A pending intent is executed twice, a stale graph is trusted, or a second ledger resets usage | Exclusive reservations, preserved counters and explicit trust boundary; future executor checks current graph/permissions, enforces deadlines, and reconciles all model/validator usage against the authoritative ledger | Maintainer | Local controls verified in #5; live integration remains #6/#7/#8 |
| R-009 | Mutable GitHub records, ambiguous network writes or stale exports are mistaken for fresh dispatch authority | Medium | High | Duplicate comment, missing receipt, stale structured status, closed task without accepted evidence | Exclusive committed publication claims, full pagination and pinned receipt verification, append-only history, live drift checks and explicitly read-only recovery; no automatic uncertain POST retry | Maintainer | #6 validates metadata and recovery; executor/reviewer remain #7/#8 |
| R-010 | Declared reviewer/implementer identities are mistaken for authenticated ones, so a misdeclared model family defeats the cross-family gate | Medium | High | An acceptance record whose reviewer family cannot be traced to a routing decision or operator record | Identities are recorded and auditable in the acceptance ledger; independence refusals at every authority point; the protocol states the declaration boundary plainly; route reviewers through the router where possible | Maintainer | Known boundary stated in ACCEPTANCE_PROTOCOL.md; delivered in #8 |
| R-011 | A concurrent Claude session writes files into the working tree mid-session, contaminating commits or failing drift checks | Medium | Medium | Untracked files appearing during work; payload drift on files nobody in the session touched | `Claude outputs/` gitignored and payload-excluded; explicit path adds instead of `git add -A`; deterministic gate re-executes drift checks and catches contamination | Maintainer | Occurred three times during #8; mitigations in place, recurrence possible |
| R-012 | A patch/review loop on a gate whose safety property was never established as an invariant: each finding is answered where it was noticed and review finds the next exit path or path component | Medium | High | Two or more consecutive review rounds return findings in the same class on the same file | Stop for diagnosis when a class recurs; write the invariant as an ADR before code; give each invariant one owner in code and one regression that asserts the invariant rather than the symptom (ADR-024) | Maintainer | Occurred on PR #22 (26 findings, 15 reviews); rule now recorded in HANDOFF and the ADR |
| R-013 | A hardware evidence record is an operator declaration; a fabricated or copied record with a valid digest satisfies the hardware-rung attestation rule | Low | High | An attested hardware rung whose record names a device or run no one can corroborate, or whose artifacts are absent | The record shape demands contradictable detail (device identity, firmware, setup, expected and observed behavior, artifacts by reference and digest); the attesting operator must be the record's operator and not an implementer; `status --evidence-dir` re-verifies digest, task, validation, rung, outcome and operator and `status` without it says its basis is attestation, not record verification (ADR-027); the protocol states the boundary plainly | Maintainer | Known boundary stated in examples/software-hardware/README.md; delivered in #9 |
| R-014 | A pull request is merged before an automated or external review of its final head has posted, so findings land in `main` unanswered | Medium | Medium | Review comments on a merged PR with no reply; findings reproducible on `main` | Standing rule recorded in MASTER_INSTRUCTIONS.md, MASTER_CLAUDE_CODE.md and .claude/rules through PR #22: never merge until a Codex review for the current head SHA exists and every finding is answered; a moved head requires re-review naming the new SHA; findings are read from GitHub only | Maintainer | Occurred on PR #21 (four findings, answered by reopening #8 through PR #22); rule in force from PR #22 onward |
