# Issue #8 validation and review

Issue: [Build independent review, acceptance gates, and minimal-context review packets](https://github.com/henslewm/universal-ai-project-template/issues/8). #7 was closed through merged PR #20 at `b326dca1674ae858eacb83cda7cf67c96c2d0e12` before this child began. Locked master #14 title/body and order remain unchanged. The design was approved by the maintainer before implementation, with three explicit decisions: the deterministic gate executes checks itself; risk-tier gate floors are protocol constants that packets and configuration can only tighten; and cross-family review at high risk is a hard gate with an explicit recorded waiver.

## Acceptance mapping

- **Review requirements are assigned in the work packet.** `REVIEW_FLOORS` in `scripts/work_packet.py` binds each risk tier to a gate floor — low: deterministic; medium: + model review; high: + cross-family; critical: + architect review and user decision. A contract's optional `review.required_gates` block may add gates and is refused below its floor; project configuration may add gates per risk and can never remove one; and a contract repair can no longer change `risk` or `review`, so a wording repair cannot lower the gates.
- **Review cannot silently change scope.** The reviewer report shape is closed: no contract field exists to edit, an unexpected field is refused, and every named contract failure must reference an existing criterion, validation, or scope/architecture rule. A change that needs a wider contract is `NEEDS_ESCALATION` or `ARCHITECTURE_CONFLICT`, never a corrective action; the same rule is re-enforced when the condensed decision enters the task ledger.
- **Rejections identify bounded corrective action.** `REJECT_BOUNDED` requires named contract failures each carrying evidence and a corrective action performable inside the current contract. The rejection overturns the worker's objective `PASS` (its routing outcome becomes `FAIL` with the rejection fingerprint, preserving the raw result — the same pattern as blocker resolution), so the router dispatches the corrective attempt inside the same frozen budget, with the failures carried into the next brief as `review_rejections`. A repeated identical rejection escalates to the architect instead of looping, and reviews are bounded by `max_review_attempts`.
- **High-risk work receives independent review.** An implementation actor cannot open a review of, attest, waive, decide, or accept its own revision, in every case by recorded-identity comparison. At high and critical risk the approving reviewer's declared model family must differ from every implementation actor's, or an explicit `waive-cross-family` with operator and reason is recorded and becomes acceptance evidence; the waiver is cleared by resubmission.
- **Premium reviewer context is minimized.** The review packet is rendered only from the acceptance ledger's own records — contract revision, worker result labeled as supplied, artifact by content-or-reference with digest, deterministic-gate observations labeled as independently observed, attestations, prior rounds, open questions, and a report contract whose field shapes are read from the schema. Both rendered forms are bounded and credential-scanned. The dogfood packets below were 13,162 and 15,431 characters for a six-criterion contract.
- **Task closes only after required gates pass.** `accept` refuses unless the deterministic gate is satisfied for the current submission, every required review gate has a current-submission approving review, the cross-family rule or its waiver holds, and any required user decision is an approval. An approval alone cannot close the feedback task — `sync-feedback` emits `APPROVE` only from a recorded `ACCEPT` — and the feedback controller's `REVIEW_PENDING` exits only through a recorded review decision.

## Dogfood — Issue #8 reviewed through its own machinery

Before closure, #8's own diff was put through a real acceptance ledger (11 events, preserved at `_acceptance-demo` outside this repository). The packet `ISSUE-8-ACCEPTANCE` carried this issue's six acceptance criteria and one validation whose declared command re-executes the full suite, repository validation and payload sync. The reviewer was a fresh Claude subagent given exactly three files — the reviewer rules, the rendered review packet, and the digest-bound diff — and nothing else.

**Round 1 — Gate D caught real drift the implementer's claim missed.** The first `run-checks` failed: `sync_skills --check` reported payload drift from a stray file a concurrent Claude session had saved into the working tree minutes earlier. The implementer's supplied result asserted a clean run; the independently observed execution contradicted it. The event stands in the ledger.

**Round 1 review — a real gate-bypass defect, REJECT_BOUNDED.** The reviewer found that a review-gate approval recorded before a `RESUBMIT` still satisfied that gate for the resubmitted artifact: `RESUBMIT` cleared checks, attestations, waiver and user decision but not reviews, and gate satisfaction took the latest completed review per gate with no submission binding. At critical risk under shipped defaults, a model-review approval of a superseded artifact plus a post-resubmission architect approval could close a submission the model-review gate never examined. The rejection named the failing criterion, the exact mechanism, and a corrective action inside the contract. `verify-review` validated the report; `ingest-review` recorded it; the ledger moved to `REJECTED`.

**Correction (`8490b55`).** Each review now records the submission it was opened for; gate satisfaction consults only current-submission reviews; attempt counting and rejection fingerprints still consult all reviews. A regression replays the reviewer's exact sequence and asserts `accept` refuses until a fresh model review examines the resubmitted artifact.

**Round 2 — APPROVE and acceptance.** After `resubmit`, a clean Gate D run (284 tests, 67 paths, 0 drift, exit 0, workspace digest `377388aa…`), and a fresh reviewer packet carrying the round-1 rejection in `prior_reviews`, a new subagent verified the correction against the prior corrective action, re-verified every criterion on its own merits, and approved with all six criteria met. `accept` then recorded `ACCEPTED` with the gate summary and the decision evidence referencing both review ids and the ledger head hash.

This round-trip is the machinery's own demonstration: the deterministic gate contradicted a supplied claim with an observation, the reviewer rejected with bounded corrective action, the correction was regression-tested, and closure was granted only by the recorded gates.

## Explicit boundaries

The deterministic gate executes only commands the architect committed into the contract, in the reviewed workspace; it never invokes a model, never runs a harness, and executing a check is not accepting work. Reviewer actor, model family, implementers, attesting operators and deciders are recorded declarations the controller cannot authenticate — a misdeclared reviewer family defeats the cross-family gate the way an understated context window defeats the capacity gate, and the declaration is auditable in the record rather than invisible. Evidence a reviewer cites is evidence from the packet; the controller does not verify external claims. Acceptance justifies but does not perform merge, publication, or issue closure. The template remains deliberately unactivated; nothing in #8 activates autonomy or expands permissions.

## Decisions

- **ADR-014** — the deterministic gate executes the contract's declared validation commands itself; the one exception to the metadata-only pattern, because independence requires observation rather than transcription.
- **ADR-015** — risk-tier gate floors are a single protocol declaration; packets and configuration may only tighten, and contract repair cannot change risk or the review block.
- **ADR-016** — cross-family review at high risk is a hard refusal with an explicit recorded waiver that becomes acceptance evidence.
- **ADR-017** — review-gate satisfaction is bound to the current submission, and a bounded rejection overturns the objective PASS so the corrective attempt is routable inside the frozen budget.
