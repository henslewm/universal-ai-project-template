# Bounded execution harness

A worker harness executes one architected work packet and nothing else. Cline is the default harness; it is not the architect and not a source of truth. This implements Issue #7.

The harness sits in exactly one gap: between the reservation the feedback controller grants and the result it records. Everything around that gap already exists and is reused rather than duplicated. `WORK_PACKET_PROTOCOL.md` owns the contract and its revisions. `MODEL_ROUTING.md` owns tier and effort selection and its replayable decision ledger. `FEEDBACK_PROTOCOL.md` owns the reservation, the attempt budget, failure evidence and escalation. `GITHUB_LEDGER_PROTOCOL.md` owns publication of the resulting evidence. No routing decision, attempt counter or scope rule lives inside the harness or inside Cline.

`scripts/execution_harness.py` never invokes a model, never runs the harness command, and never verifies that reported work actually happened. It prepares a bounded brief, emits the exact invocation, and ingests a report. An operator or a later authorized automation runs the harness itself.

## Setup and authority

1. Copy `config/execution-harness.example.json` to project-specific configuration. The committed example is `enabled: false` and every model identifier in it is a placeholder; replace them with the real resource ids your router configuration declares.
2. Each binding maps one routed resource id to one harness, provider, model and optional API base. A local OpenAI-compatible server is named by its URL; cloud credentials are named **only** by environment variable, never embedded. Configuration validation refuses credential-like material anywhere in the file, unknown `{placeholder}` names, a templated command, a binding without `{brief}` or `{report}`, duplicate harness ids and duplicate resource bindings.
3. Confirm the harness flag names against the installed harness version before enabling. This adapter never runs the command, so a wrong flag surfaces when the operator runs it rather than silently. The committed example was confirmed against Cline CLI 3.86.2, where three things matter:
   - `--data-dir` gives the run its own isolated state, so a bounded run never reads or rewrites the operator's global Cline configuration. Prefer it for every dispatch.
   - The CLI has no output-file flag, so the worker writes the report itself. The brief's report contract is what makes that reliable, and `ingest` refuses a report that does not match it.
   - `--provider lmstudio` uses the native local provider and rejects `--base-url`; an OpenAI-compatible provider accepts a base URL instead. Either satisfies a local server. `cline auth` also insists on an API key argument even for a local server that ignores it, so name a placeholder through `credential_env` rather than inlining a literal — the configuration validator refuses credential-like material.
4. Declare each harness's own `context_overhead_tokens` — what it consumes before the brief is read — `limits.chars_per_token`, the conservative divisor used to estimate the brief, and `limits.context_growth_reserve_tokens`, the room a run needs after its opening prompt. Where a resource is served in a smaller window than the router configuration declares, state that window in the binding's `served_context_window`; a binding may never claim more than the resource declares. Measure the overhead against the installed version. On Cline CLI 3.86.2 the system prompt and tool definitions were observed to consume roughly 6805 tokens before any brief, which is most of an 8192-token window on its own.
5. Dispatch preparation requires `enabled: true`. Everything else — approval, the bound configuration digest, the attempt budget — is enforced by the controllers this harness defers to.

```text
python scripts/execution_harness.py --config config/execution-harness.json validate-config
python scripts/execution_harness.py --config config/execution-harness.json verify-report RUNDIR/brief.json RUNDIR/report.json
python scripts/execution_harness.py --config config/execution-harness.json --root . dispatch LEDGER RUNDIR --router-config config/model-router.json --request request.json
python scripts/execution_harness.py --config config/execution-harness.json ingest LEDGER RUNDIR/report.json
python scripts/execution_harness.py --config config/execution-harness.json abandon LEDGER --reason "..."
```

## Worker cycle

Read startup instructions and packet → identify scope, validation and stop conditions → inspect allowed task context → implement or analyse → run the specified validation → report bounded evidence → retry within budget or return escalation state.

Every new dispatch includes a `startup` block in `brief.json`, with `role: worker`, ordered startup steps and complete instruction snapshots under `documents`. Each snapshot records `source` (`project` or `harness`), repository-relative `path`, `sha256` and `content_lines`; joining those lines reconstructs the full text. The worker reads every line before implementation. This is automatic for every harness that receives the brief, including replacement harnesses that do not accept a separate rules path.

The dispatcher always supplies `MASTER_INSTRUCTIONS.md`, `AUTONOMY_CONTROL_PLANE.md`, `PROJECT_CHARTER.md`, `WORK_PACKET_PROTOCOL.md` and `EXECUTION_HARNESS_PROTOCOL.md` from the project root. It includes root `AGENTS.md` and `CONTRIBUTING.md` when present, plus the harness's `BOUNDED_WORKER_RULES.md`. Project configuration may append required relative paths through `startup_documents`, for example `["src/AGENTS.md", "MASTER_CODEX.md", "docs/task-handoff.md"]`. The architect supplies applicable platform/path instructions and task handoffs there; prose `context_scope` cannot reliably identify them automatically. Missing required files, empty/unreadable files, unsafe paths, links or credential-like instruction contents refuse preparation before a reservation is spent. Instruction text is bounded and included in the brief/context-capacity checks; it is never silently truncated to fit a model.

The startup also directs the worker to the contract, architect guidance, prior failures and review rejections already embedded in the brief. These carry task-specific corrections forward without another handoff document or a reminder from the user. A worker identifies the permitted edits, required checks and stop conditions before work. Missing task inputs stop dependent work; conflicts with governance require `ARCHITECTURE_CONFLICT`. The bundle supplies read-only governance, not broader implementation permission. Applicable local instructions encountered inside permitted task context must be read before editing; inaccessible required context is reported rather than sought outside the boundary.

This role-specific startup replaces a bounded worker's general repository-history startup and repository-wide closeout. Manual worker chats follow the equivalent rule in `MASTER_INSTRUCTIONS.md`; native startup routers point there. Independent reviewers are a separate role: their generated review packet and restricted evidence boundary remain unchanged. Start sealed reviews in isolated review directories without unrelated native repository imports.

`feedback.reserve` still verifies active bootstrap and the matching approved architecture before granting a reservation. That remains the dispatched worker's bootstrap preflight; the worker does not repeat generic repository-level commands in its isolated workspace. It runs exactly the checks declared by its contract. The launcher remains responsible for current permission and reservation/deadline controls. Manual workers without a harness dispatch still perform the normal bootstrap check. No prepared brief grants authority or substitutes for acceptance.

New worker briefs use schema version `1.1` and require the startup block. Ledger-free report verification continues to recognize exact legacy `1.0` briefs as historical artifacts. Worker report fields, acceptance gates and ledger replay are unchanged. Delivery and file integrity are mechanically checked; semantic conflicts and reading comprehension remain worker responsibilities, and a startup acknowledgement is not proof of compliance.

`dispatch` reserves one attempt through the feedback controller and writes a run directory containing `brief.json`, `BOUNDED_WORKER_RULES.md`, an empty `workspace/`, and `invocation.json` with the exact argv and the environment variable names required. The argv is built from `{rundir}`, `{workspace}`, `{brief}`, `{report}`, `{rules}`, `{provider}` and `{model}`; no other placeholder is accepted, and every one must be substituted. It does not create `report.json`; the worker writes that. A run directory is never reused, so evidence is never overwritten, and it is created only once an attempt exists: a reservation the controller refuses leaves no directory behind to block the retry.

Preparation also checks capacity, which no controller above it can. The router compares the architect's declared token estimate against the resource's declared context window; it cannot see what the harness adds afterwards — the rendered brief, the worker rules and the harness's own system prompt — nor that a locally hosted model is served in the window it happened to be loaded with. So `dispatch` sums the declared harness overhead, the measured brief, the rules, the reserved output tokens and the declared growth reserve, and refuses when that exceeds the served window, reporting the arithmetic as `context_estimate` on a prepared dispatch. The growth reserve matters because the check covers the opening prompt only: a worker's context grows with every tool result it reads, and the passing operator run grew from 5,480 to 13,649 tokens across nine iterations, so a dispatch sized to its first turn alone can still exhaust the window halfway through. The reserve is an operator declaration calibrated from observed runs of comparable packets, not a prediction. The estimate is a character-count approximation and deliberately conservative; it is not a tokenizer, and an understated `context_overhead_tokens`, `context_growth_reserve_tokens` or an overstated `served_context_window` will still let an impossible dispatch through. A binding that claims more than its routed resource declares is a configuration contradiction rather than a capacity question, so it is refused before a reservation is spent and never costs a bounded attempt. Its purpose is to turn a failure the worker meets on its first tool call into a refusal with stated numbers.

The brief carries the packet-permitted task context plus the mandatory read-only startup governance. It is rendered from the controller's own worker context — the current contract revision, the controller status, remaining and per-tier attempt budgets, architect guidance, prior failure fingerprints and summaries — plus the harness binding, startup bundle and report contract. There is no second, looser copy of the contract for the worker to read, and the brief is refused if it exceeds its configured bound or contains credential-like material. The bound and the credential scan apply to the indented file the worker is actually handed, not only to its canonical form, because those differ in size.

`ingest` validates the report before it reaches the ledger: exact field set, a dispatch id matching the pending reservation, one validation check per contract validation id and no invented ids, non-empty evidence, a size within bound, no credential-like material, and `PASS` only when every check passed, scope is `within` and no architecture conflict is reported. A report that fails any of these is refused rather than recorded, so a worker cannot silently broaden its packet or grade itself.

## Failure, escalation and replaceability

A failed attempt is recorded with its evidence and fingerprint, and the next brief carries that evidence forward. A stronger tier therefore receives what was already tried instead of rebuilding context.

A worker that writes no report, or writes one the validator refuses, is a real outcome but never an inferred one. `ingest` refuses both and leaves the reservation untouched; `abandon` closes it, recording the operator's stated reason as the attempt's evidence. Because nothing was reported, scope is genuinely unknown, so the controller moves to an architect decision rather than looping a worker that may be structurally unable to complete the packet. The reason is required, bounded and credential-checked; absence alone never closes an attempt.

If preparation refuses after the reservation is already spent — no binding for the routed resource, an oversized brief, a brief that cannot fit the window the resource is served in — the attempt is closed as `PROVIDER_UNAVAILABLE` with the refusal as evidence rather than left pending. The controller escalates that to the architect rather than retrying, which is deliberate: a harness that cannot be prepared is an architecture or configuration problem, not a transient failure to loop on.

Cline is replaceable. Any harness that accepts a brief path and writes a report path can be bound instead, which is why the example declares a second non-Cline harness. Packets, contracts, routing decisions, attempt ledgers and published evidence remain valid across that substitution. Nothing here assumes a harness can natively assign a different model to every arbitrary subagent; the orchestration layer stays explicit precisely so that assumption is never load-bearing.

## Boundaries

No credential belongs in configuration, briefs, reports, run directories, logs or comments. The adapter records assertions a worker makes about its own validation, cost and scope; those are supplied evidence, not proof. It does not authenticate roles, verify that a model was called, confirm that a command was actually run, or accept work. Independent acceptance remains Issue #8. `verify-report` applies the same report contract to a brief and report pair without a ledger. It records nothing and accepts nothing; it exists so an operator-run demonstration can be checked by the real validator rather than by eye. A live run against a real local model is an operator action whose transcript is evidence for that run only and is not reproducible in CI.
